# Phase 02.1: Fix Moon Velocity and Rename vlong API - Research

**Researched:** 2026-02-12
**Domain:** Astronomical calculations, API design
**Confidence:** HIGH

## Summary

This phase addresses two critical bugs discovered during Solaris integration:

1. **Moon velocity calculation bug**: When the Moon's longitude crosses the 360°/0° boundary, `vlong()` returns wildly incorrect values (e.g., -36000°/day instead of +14°/day). This is a longitude wrapping bug in the finite difference calculation.

2. **API naming ambiguity**: The function name `vlong()` is ambiguous - the "v" prefix could mean "value" or "velocity", leading to confusion and incorrect usage. Claude has misinterpreted `vlong` as "longitude value" instead of "longitude velocity" when assisting with Kala integration.

**Primary recommendation:** Fix the Moon velocity wrapping bug by handling the 360°/0° boundary correctly, and rename `vlong()`/`vlat()`/`vdist_au()` to use explicit `_velocity` suffix for clarity.

## Bug Analysis

### Bug 1: Moon Velocity Wrapping

**Location:** `ketu/ephemeris/planets.py`
- Lines 101-110 (scalar calculation)
- Lines 463-472 (vectorized calculation)

**Root cause:** The finite difference calculation does not handle longitude wrapping:

```python
# Current (BROKEN):
lon_speed = (lon2 - lon) / jd_delta
```

When Moon longitude crosses 360°→0°, this calculates:
- `lon1 = 359.87°`, `lon2 = 0.02°`
- `lon_speed = (0.02 - 359.87) / 0.01 = -35985°/day` ❌

Should be:
- `lon_speed = (360.02 - 359.87) / 0.01 = 15°/day` ✓

**Verified example:**
- Date: 2024-01-16 05:00:00 UTC
- Position at t: 359.873076°
- Position at t+δ: 0.015521°
- **vlong() returns:** -35985.755491°/day (WRONG)
- **Correct velocity:** 14.244509°/day
- **Error:** -36000°/day (exactly -360° offset)

**Impact:**
- Occurs once per lunar month (every ~27 days when Moon completes 360° orbit)
- Affects cycle calculations in Solaris/Kala that rely on accurate lunar velocity
- Causes incorrect cycle phase predictions during Moon's sidereal month transitions
- No other bodies affected (Sun ~1°/day, planets much slower, unlikely to wrap in 0.01 day interval)

## Architecture Patterns

### Pattern 1: Angle Wrapping in Finite Difference

**What:** Handle angular wrapping when calculating derivatives via finite differences

**When to use:** Any time you compute velocity/speed from angular positions that can wrap around 360°

**Standard approach:**
```python
# Calculate difference with wrapping
diff = angle2 - angle1
if diff > 180:
    diff -= 360
elif diff < -180:
    diff += 360
velocity = diff / time_delta
```

**Why this pattern:**
- Ensures shortest angular distance is used
- Handles both forward wrapping (359°→1°) and backward wrapping (1°→359°)
- Standard in astronomy/navigation software

**Examples in existing code:**
- `ketu/calculations.py:57-58` - `distance()` function already handles wrapping correctly
- `tests/test_direct_new_moon.py:38-45` - User code correctly handles wrapping

### Pattern 2: Explicit Naming for Domain-Specific Functions

**What:** Use full descriptive names for functions with potential ambiguity

**When to use:** When abbreviated names could have multiple interpretations

**Current precedent in codebase:**
- `body_properties()` - full name, clear meaning
- `dist_au()` - explicit unit suffix `_au`
- `utc_to_julian()` - explicit transformation direction

**Recommended naming:**
```python
# From:
vlong()  # ambiguous
vlat()   # ambiguous
vdist_au()  # semi-clear

# To:
long_velocity()  # explicit
lat_velocity()   # explicit
dist_velocity_au()  # explicit
```

Alternative considered: `velocity_long()`, `velocity_lat()`, `velocity_dist_au()`
- **Tradeoff:** Prefix makes autocomplete easier but breaks convention with `long()`, `lat()`, `dist_au()`

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Angle wrapping | Manual mod 360 logic with edge cases | Standard -180/+180 normalization pattern | Edge cases around ±180° boundary, retrograde motion, multiple wraps |
| API deprecation | Delete old functions immediately | Deprecation warnings + aliases | Breaking change requires major version, allows migration period |

**Key insight:** Angle arithmetic has subtle edge cases (negative angles, retrograde motion, multiple wraps). Use battle-tested patterns.

## Common Pitfalls

### Pitfall 1: Forgetting Wrapping in Vectorized Code

**What goes wrong:** Fixing scalar code but not vectorized variant (or vice versa)

**Why it happens:** Moon velocity calculated in TWO places:
- `calc_planet_position()` - scalar (lines 101-110)
- `calc_planet_position_batch()` - vectorized (lines 463-472)

**How to avoid:**
- Fix BOTH implementations
- Add test that exercises both code paths
- Verify vectorized and scalar produce identical results

**Warning signs:** Test passes for some dates but fails when Moon crosses 360°

### Pitfall 2: Not Handling Latitude Wrapping

**What goes wrong:** Latitude can also wrap, but differently (±180° vs ±90° for lat)

**Why it happens:** Latitude range is -90° to +90°, not 0-360°

**How to avoid:**
- For **longitude**: wrap at ±180° (correct for 0-360° values)
- For **latitude**: shouldn't wrap in normal calculations (check if body latitude exceeds ±90°)
- Moon latitude range: ~±5.14° (inclination), so wrapping not needed

**Recommendation:** Only fix longitude velocity, latitude doesn't wrap in practice for Solar System bodies

### Pitfall 3: Breaking API Without Deprecation

**What goes wrong:** Renaming function without migration path causes immediate breakage

**Why it happens:** Function is exported in public API, used in downstream code

**How to avoid:**
- Keep old names as deprecated aliases
- Add deprecation warnings
- Document migration in UPGRADING.md
- Plan removal for next major version (0.5.0 or 1.0.0)

**Warning signs:** Import errors, test failures in downstream projects

def test_moon_velocity_wrapping():
    """Verify Moon velocity is correct when crossing 360°/0° boundary.

    from datetime import datetime, timezone

2. **Should we normalize all body longitudes to 0-360 after calculation?**
