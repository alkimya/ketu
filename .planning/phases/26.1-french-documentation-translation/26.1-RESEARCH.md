## 2. Charset Header Fix

### The Bug

Five files (`arabic_parts.po`, `chiron.po`, `houses.po`, `predictive_charts.po`,
`relational_charts.po`) have a blank header block — the msgstr for the header entry is `""`.
`msgfmt` refuses to compile them (`fatal error: .po file header absent or invalid;
charset conversion will not work`). These 5 files were created by `sphinx-intl update` in
Phase 25 from empty .pot template files that produced an empty header.

### Why update-po Does NOT Fix This

`sphinx-intl update` only rewrites a .po file when its msgid set changes vs the .pot. The
source pages for these 5 files have not changed since Phase 25. So running `make update-po`
returns "notchanged" and leaves the files unmodified — charset stays missing.

**`msgconv --to-code=UTF-8` also fails** because it requires a charset to be declared in
the input file to do the conversion.

### Recommended Fix: Babel Python Script (VERIFIED WORKING)

Use `babel.messages.pofile` (already in venv — babel 2.18.0) to read, set proper metadata,
and write back. Babel's `read_po` auto-detects utf-8 for charsetless files and its
`write_po` emits a complete header including `Content-Type: text/plain; charset=utf-8`.

**Exact script** (run from repo root, no cd needed):

```python
from babel.messages import pofile

FILES = [
    'docs/locale/fr/LC_MESSAGES/arabic_parts.po',
    'docs/locale/fr/LC_MESSAGES/chiron.po',
    'docs/locale/fr/LC_MESSAGES/houses.po',
    'docs/locale/fr/LC_MESSAGES/predictive_charts.po',
    'docs/locale/fr/LC_MESSAGES/relational_charts.po',
]

MIME_HEADERS = [
    ('Project-Id-Version', 'Ketu 1.3.0'),
    ('Report-Msgid-Bugs-To', ''),
    ('POT-Creation-Date', '2026-06-01 17:04+0200'),
    ('PO-Revision-Date', '2026-06-01 00:00+0200'),
    ('Last-Translator', 'Claude AI <noreply@anthropic.com>'),
    ('Language', 'fr'),
    ('Language-Team', 'fr <LL@li.org>'),
    ('Plural-Forms', 'nplurals=2; plural=(n > 1);'),
    ('MIME-Version', '1.0'),
    ('Content-Type', 'text/plain; charset=UTF-8'),
    ('Content-Transfer-Encoding', '8bit'),
    ('Generated-By', 'Babel 2.18.0'),
]

for fpath in FILES:
    with open(fpath, 'rb') as f:
        cat = pofile.read_po(f, charset='utf-8')
    cat.mime_headers = MIME_HEADERS
    cat.locale = 'fr'
    cat.charset = 'utf-8'
    with open(fpath, 'wb') as f:
        pofile.write_po(f, cat, width=76)
    print(f'Fixed: {fpath}')
```

**Verified**: After running this script, `msgfmt --statistics` on all 5 files returns entry
counts without warnings. Entry content is preserved (42 entries in arabic_parts.po before
and after). Use `/home/loc/workspace/ketu/venv/bin/python` to run (babel is in venv, not
system Python).

**Survives future update-po?** Yes. If `make update-po` is run later (e.g., for a docs
edit), babel writes the file again WITH the charset, so it persists. The fix is
idempotent.

## 3. Translation Workflow

### Direct .po Edit vs Babel Script

**Recommendation: Direct .po text editing** for the main translation work.

**Why**: Each executor agent will read the .po file, translate the empty `msgstr` entries,
and write them back. Direct editing is simpler, faster, and less error-prone for bulk text.
The risk with babel round-trips is that `write_po` reformats line-wrapping at 76 chars —
this can unnecessarily diff already-translated entries. Direct editing preserves the exact
existing formatting.

**When to use babel script**: Only for the charset header fix (Plan 01). For translations,
edit .po directly.

### Multiline msgid Handling

The most common multiline pattern is:
```
msgid ""
"First line of text that "
"continues on second line."
msgstr ""
```

The `msgstr` for a multiline entry must also use the same quoted-string concatenation:
```
msgid ""
"First line of text that "
"continues on second line."
msgstr ""
"Première ligne de texte qui "
"continue sur la deuxième ligne."
```

Or it can be a single line if the translation is short enough. Line wrapping at 76 chars
is cosmetic — Sphinx/babel accept both forms.

**Simpler alternative for multiline entries**: Use a single-line msgstr:
```
msgstr "Première ligne de texte qui continue sur la deuxième ligne."
```
This is fully valid and avoids the wrapping complexity. Use this approach for entries
under ~120 chars translated; multi-line for longer entries.

## 4. Marker-Preservation DO/DON'T Rules

These rules are extracted from Phase 25-03 experience and MyST-markdown gettext behavior.

### DON'T — Causes Warnings or Broken Rendering

| Pattern | What it breaks |
|---------|---------------|
| `msgstr "# Titre"` when `msgid "Titre"` | `myst.header` WARNING (heading level mismatch) — the exact bug Phase 25-03 fixed in `performance.po` and `installation.po` |
| `msgstr "## Référence API"` when `msgid "API Reference"` | Same — `##` prefix in msgstr when msgid has no `##` |
| Translating `{ref}\`genindex\`` | Breaks cross-reference resolution; these are Sphinx roles |
| Translating `{doc}\`...\`` or any `{role}\`...\`` | Same — all MyST roles must be verbatim |
| Translating code-only msgids like `` `ketu.parts` `` | The backtick span IS the content; "translate" = copy verbatim |
| Dropping `\`\`` backticks from inline code | Breaks `code` rendering in HTML |
| Changing URL strings | Breaks links |
| Translating function signatures: `` `long(jday, body)` `` | Code identifiers are not natural language |

### DO — Required for Correct French

| Pattern | Correct behavior |
|---------|-----------------|
| `msgid "API Reference"` → `msgstr "Référence API"` | Translate prose headings |
| `msgid "**Parameters:**"` → `msgstr "**Paramètres :**"` | Keep `**bold**` markers; translate text; add FR space before colon |
| `` msgid "`jday` (`float`): Julian Day number" `` → `` msgstr "`jday` (`float`) : Jour Julien" `` | Keep backtick code verbatim; translate the description; add FR space before colon |
| `msgid "House Systems"` → `msgstr "Systèmes de maisons"` | Translate section headings |
| `msgid "{ref}\`genindex\`"` → `msgstr "{ref}\`genindex\`"` | Preserve verbatim |
| Table cell content (single words) → translate if prose | Table cells that are code/identifiers copy verbatim |

### The FR Colon Rule

In French, a space is required before `:`, `;`, `!`, `?`. Apply this consistently:
- `**Parameters:**` → `**Paramètres :**`
- `` "`jday` (`float`): Julian Day" `` → `` "`jday` (`float`) : Jour Julien" ``

### Code-Only msgid Pattern

Any msgid that is ENTIRELY a code span (starts and ends with backtick) must be reproduced
verbatim. Examples:
- `` `positions(jday, l_bodies=bodies)` `` → copy verbatim as msgstr
- `` `ketu.composite` `` → copy verbatim
- `` `CHART_DTYPE` `` → copy verbatim

These appear in the api.po and architecture.po heavily. Verified count: 39 code-only entries
in api.po alone. They are valid translations (identity) and required for the docs engine.

### Glossary Consistency Rule

The planner must include the glossary table (Section 7) as context in EVERY translation
plan's task definitions. An inconsistency — e.g., one plan using "Carré" and another using
"Quadrature" for Square — would be confusing for French readers. The glossary is the
single source of truth.

### FR Typography Rules (brief reminder)

- Space before `:`  `!`  `?`  `;` → e.g., `Paramètres :` not `Paramètres:`
- Decimal separator: `,` not `.` for French numbers — but keep English numbers in code/formulas
- Quotation: « » guillemets for prose quotes; backtick for code as-is
- Gender: "le module", "la fonction", "le tableau" (all masculine for tech terms)
