# Requirements: Ketu v1.1 Flexibility & Houses (ARCHIVED)

**Defined:** 2026-05-06
**Shipped:** 2026-05-08
**Core Value:** Cycle calculations must be correct, tested, and performant
**Milestone goal:** Make Ketu more flexible (configurable aspects), more complete (astrological houses), and more correct (Lilith fix) — evolving from astronomical to astronomical-astrological framework.

> **ARCHIVE NOTE:** All v1.1 requirements were validated and shipped in v1.1.0 (PyPI 2026-05-08). The Lilith formula correction shifted longitudes by approximately 180° — documented as BREAKING with magnitude tables in CHANGELOG and UPGRADING. The CLI default flipped from EXTENDED (14 aspects) to CLASSICAL (5) — Kala and other downstream adapters must opt-in to EXTENDED. The `ketu.ephemeris.calculate_house_cusps` placeholder was removed in favor of `ketu.calculate_houses` with registry dispatch.

## v1.1 Requirements (All Shipped)

Requirements for milestone v1.1. Each maps to roadmap phases (numbered from 8 onwards, continuing v1.0).

### Configurable Aspects (ASP)

- [x] **ASP-01**: `core.aspects` constant remains length 14, append-only — invariant test guarantees order and length (sha256 byte fingerprint pinned in Plan 09-03)
- [x] **ASP-02**: Module `ketu/aspects/presets.py` exposes `CLASSICAL` (5 majors), `TRADITIONAL` (7 = h12), `EXTENDED` (14 = legacy v1.0)
- [x] **ASP-03**: `calculate_aspects()`, `calculate_aspects_vectorized()`, `calculate_aspects_batch()` accept `aspects=` parameter (list of names, preset name, or index array); also `find_aspects_between_dates`
- [x] **ASP-04**: Python API default changes — `aspects=None` resolves to `CLASSICAL` (5 majors); downstream consumers like Kala must explicitly request `EXTENDED` for legacy 14
- [x] **ASP-05**: `aspect_set` is resolved to a NumPy boolean mask once at API entry — no filter inside hot loops (resolver-once-above-hot-loop pattern)
- [x] **ASP-06**: LRU cache keys include `aspect_set` hash where applicable (no stale results after config change) — documented in module docstring + resolver docstring
- [x] **ASP-07**: Integration test: configure `CLASSICAL`, call all public aspect APIs, assert no result contains a non-classical aspect — covers all 4 public APIs
- [x] **ASP-08**: Benchmark: `calculate_aspects_batch()` regresses by no more than 5% vs v1.0 baseline — outcome: -10.10% (i.e., FASTER than baseline) on EXTENDED across all batch sizes

### CLI Refactor (CLI)

- [x] **CLI-01**: `ketu` command uses argparse with subcommands (replaces interactive `input()` prompt) — `display.py:main()` deleted
- [x] **CLI-02**: Flag `--harmonics SPEC` accepts preset name (`classical`, `traditional`, `extended`, `all`) OR explicit harmonic list (`9,10,11`); bare-integer rejected with clear error
- [x] **CLI-03**: `--harmonics all` returns deterministic v1.1 byte-stable output (Option A reinterpretation: forward-pin v1.1 instead of backward-pin v1.0, since Phases 8+9 deliberately diverged from v1.0 astronomy)
- [x] **CLI-04**: `ketu houses` subcommand: `--date ISO --lat FLOAT --lon FLOAT --system {placidus,koch,porphyry}` with `--polar-fallback {raise,porphyry}`
- [x] **CLI-05**: Introspection flags `--list-aspect-sets` and `--list-house-systems` print available options with descriptions
- [x] **CLI-06**: CLI output includes resolved config header on STDERR (e.g. `# Aspect set: classical (5 aspects: Conjunction 0°, Sextile 60°, Square 90°, Trine 120°, Opposition 180°)` and `# House system: placidus`)

### Houses Module (HOU)

- [x] **HOU-01**: `sidereal_time()` audited and tightened to APPARENT GST (mean GMST + nutation × cos(eps_mean)) per Meeus eq. 12.6; aligned with Swiss Ephemeris house functions
- [x] **HOU-02**: `ketu/houses/` subpackage with registry pattern (`SYSTEMS = {"placidus": ..., "koch": ..., "porphyry": ...}`) for extensibility
- [x] **HOU-03**: Placidus implementation with iteration cap (MAX_ITER=50) and explicit non-convergence handling (NaN propagation)
- [x] **HOU-04**: Koch implementation (closed-form ad3 trisection of equator's ascensional difference projected via Asc1; bit-exact match vs swisseph case 'K')
- [x] **HOU-05**: Output `HOUSES_DTYPE` structured array: 12 cusps + ASC + MC + ARMC + Vertex
- [x] **HOU-06**: Polar fallback parameter `polar_fallback={"raise","porphyry"}`; `HighLatitudeError` raised by default beyond ±66.56°
- [x] **HOU-07**: Helper `house_of(planet_lon, cusps) -> int` returns 1-12 (vectorized)
- [x] **HOU-08**: Vectorization over `(jd, lat, lon)` arrays (mask-based continuation for Placidus iteration)
- [x] **HOU-09**: 96.75% coverage on `houses/` (≥95% gate); 10 reference charts × 3 systems oracle snapshot vs Swiss Ephemeris (incl. polar lats 70°/80°)
- [x] **HOU-10**: Removed `calculate_house_cusps` placeholder stub from `ephemeris/planets.py` (was returning wrong equal-house values) — BREAKING in CHANGELOG

### Lilith Verification & Fix (LIL)

- [x] **LIL-01**: `docs/LILITH_DEFINITION.md` written FIRST (Mean Apogee, tropical longitude, Chapront-Touz/Francou citation, explicit formula `83.3532 + 0.1114040803 * d`, 0.01° tolerance contract)
- [x] **LIL-02**: Test harness `tests/test_lilith_cross_check.py` parametrized over 5 dates (1900, 1950, 2000, 2025, 2050) vs `swe.calc_ut(jd, swe.MEAN_APOG)` — empirical max |delta| = 179.936579° (constant ~180° offset detected; branched to FORMULA-CORRECTION)
- [x] **LIL-03**: Formula corrected at 4 plumbing sites; post-fix max |delta| = 0.002693° on plan dates, 0.007815° over 55K daily samples 1900-2050 (1.85x under 0.005° regression tolerance)

- [x] **LIL-05**: CHANGELOG and UPGRADING.md document Lilith correction with magnitude (per-date table, magnitude consistency invariant across CHANGELOG / UPGRADING / LILITH_DEFINITION)

## Notes on Changed Requirements

- **CLI-03 reinterpretation:** Original contract was "byte-identical to v1.0 reference"; reinterpreted via Option A user decision in Plan 11-06 to "self-stable forward contract" — pins v1.1 format going forward, NOT v1.0 backward compatibility (which Phases 8 + 9 deliberately broke for documented astronomical reasons).
- **ASP-08 outcome:** Performance gate was "≤5% regression"; actual outcome was -10.10% (FASTER than v1.0). The hot-loop perf fix in `calculate_aspects_batch` (per-aspect work hoisted above per-date loop) introduced as part of Plan 09-05 over-delivered.

## Out of Scope (Reaffirmed)

Explicitly excluded from v1.1 (and reaffirmed at close).

| Feature | Reason |
|---------|--------|
| True/Osculating Lilith | Defer to v1.2 — Mean Lilith is de-facto standard in 95% of astrology software |
| Asteroid Lilith #1181 | Defer to v1.2+ — different body, separate effort |
| Whole Sign / Equal / Regiomontanus / Campanus houses (concrete impl) | Architecture supports them via registry; ship Placidus + Koch + Porphyry in v1.1 to prove pattern |
| Chiron, Centaurs, asteroids, fixed stars | Defer to future milestone |
| Arabic Parts / Lots | Defer to future milestone |
| Timezone handling inside Ketu | UTC remains required; timezone conversion is caller's responsibility |
| `pyswisseph` or `pysweph` as runtime dependency | Test-only is acceptable; license (AGPL) and brand promise (NumPy-only) prevent runtime |
| Chart/SVG visualization | Still removed since v1.0; deferred to post-Ketu GUI tooling |
| iCalendar export | Still removed since v1.0 |
| Real-time streaming calculations | Still batch-oriented |
| Web API | Ketu is a library, not a service |
| French documentation rebuild | Still deferred (`fr/CHANGELOG.md` aspirational reference only) |
| `click` / `typer` CLI dependencies | argparse stdlib was sufficient; no new runtime deps |
| Bare `--harmonics 12` integer parsing | Too ambiguous (set vs single vs range); forced named presets or explicit list |
