### Declination (DECL)

Equatorial declination δ as a first-class, vectorizable quantity, plus the Moon's biodynamic montant/descendant trajectory and out-of-bounds detection. Computation reuses the verified `coordinates.py` chain (Meeus eq. 13.4; numerically equivalent to the direct formula to machine precision).

- [x] **DECL-01**: User can compute a body's equatorial declination δ via `declination(jdate, body)` (scalar) — degrees, north +, south −, bounded [−90, +90]
- [x] **DECL-02**: `declination` is vectorizable over a `jdate` array (no Python loop in the hot path), consistent with ketu's NumPy-first contract
- [x] **DECL-03**: An equivalence regression test pins `declination` against the existing `ecliptic_to_equatorial` → `rectangular_to_spherical` chain (machine-precision agreement, Δ = 0)
- [x] **DECL-04**: User can compute the rate of change via `declination_velocity(jdate, body)` (degrees/day), forward finite-difference idiom (step mirrors `lat_velocity`); no longitude-style wraparound
- [x] **DECL-05**: User can test the Moon's montant/descendant trajectory via `is_ascending_declination(jdate, body)` (bool, True when dδ/dt > 0) — distinct from and parallel to the unchanged β-based `is_ascending`
- [x] **DECL-06**: User can test out-of-bounds via `is_out_of_bounds(jdate, body)` (bool, True when |δ| > ε), using the **instantaneous** obliquity ε(jd) (`true_obliquity`) as the threshold
- [x] **DECL-07**: `body_decl` field added to `CHART_DTYPE` (14 bodies, f8, additive, mirrors `body_lats`) — declination present in every computed chart; returns / synastry / composite inherit it
- [x] **DECL-08**: A `CHART_DTYPE` layout ratchet test guards the additive `body_decl` field change (analogue of the 13→14 body-count ratchet); downstream positional-contract impact (Kala) documented
- [x] **DECL-09**: Declination feature documented (en + fr) — the 4 functions + the aspect-centric montant/descendant framing (draconic month ~27.21 d, OOB nodal cycle) + the explicit β-vs-δ distinction

### Harmonics Debt (HARM)

Paid down the three dynamic-harmonics debts left open by v1.4. One grouped phase, order F2 → F3 → F1. The frozen `core.aspects` table + V1/V13 sha256 fingerprints stayed byte-identical throughout.

- [x] **HARM-01** (ASP-F2): `H{h}-{k}` naming scheme (k = 1..h//2) is a documented public API contract — format, ordering, bytes encoding; always `H{h}-{k}` (no traditional-name substitution by the generator)
- [x] **HARM-02** (ASP-F2): A pinning test asserts `generate_harmonic_aspects(h)['name']` exactly for representative harmonics incl. boundaries (h=2 opposition-only; even h folding to 180°; h up to 64)
- [x] **HARM-03** (ASP-F2): Documentation distinguishes the two channels — GENERATOR always emits `H{h}-{k}`; DETECTION prefers the canonical table name on angle collision (120° → Trine, not `H3-1`)
- [x] **HARM-04** (ASP-F3): `find_aspect_timing` derives the dynamic orb itself via `dyn_coef: Optional[float] = None` (`(orb[b1] + orb[b2]) / 2 * dyn_coef`)
- [x] **HARM-05** (ASP-F3): Static path (`orb=None` → `get_orb`) and explicit `orb=<float>` escape hatch both stay backward-compatible and byte-identical; precedence when both given defined + tested (explicit `orb` wins silently)
- [x] **HARM-06** (ASP-F1): User can request `--harmonics h7` (h-prefixed, case-insensitive; disambiguated from bare integer and preset/index syntax) → produces the harmonic's `h//2` aspects via `dynamic_specs=`
- [x] **HARM-07** (ASP-F1): `parse_harmonics_spec` returns a typed `HarmonicsSelection` NamedTuple (mask + dynamic_specs) clean under mypy `--strict`; grammar **Tight** — `h7` alone or comma index list; `traditional,h7` / `h7,h11` deferred
- [x] **HARM-08** (ASP-F1): v1.1 CLI byte-stability fixture stays UNCHANGED; a NEW `--harmonics h7` byte-stability fixture freshly generated + manually audited; resolved-config stderr header labels the selection
- [x] **HARM-09** (ASP-F1): `--harmonics h7` CLI surface documented (en + fr) — syntax, semantics, the Tight-grammar boundary

## Out of Scope (v1.5)

| Feature | Reason |
|---------|--------|
| Declination aspects (parallels / contra-parallels) | Touches the aspect engine (new type, orbs, detection); NOT needed by the montant/descendant core. Tracked as DECLA-01..03 |
| Changing `is_ascending` (β) to δ semantics | Would be BREAKING; β and δ are distinct, both valid. `is_ascending` UNCHANGED; δ trajectory is the new parallel `is_ascending_declination` |
| Rich `--harmonics` grammar (`h7,h11`, `traditional,h7`) | Tight grammar is the v1.5 surface. Tracked as HARMF-01 |
| Fixed 23°26′ OOB threshold | Instantaneous ε(jd) is physically correct and free |
| `body_decl` in CYCLE_DTYPE | CYCLE_DTYPE is Moon-Moon angular-separation oriented; declination belongs to chart/position surface |
| `pyswisseph` / scipy as runtime dependency | Pure-NumPy contract non-negotiable |
| Timezone handling | UTC remains required; caller's responsibility |
