**Status:** ✅ SHIPPED 2026-06-04

## Overview

Promote equatorial declination δ to a first-class, vectorizable quantity across the
whole engine — `declination` / `declination_velocity` / `is_ascending_declination`
(the Moon's biodynamic montant/descendant trajectory) / `is_out_of_bounds`, plus a new
`body_decl` field carried by every computed chart and inherited by the relational/predictive
charts — then pay down the three dynamic-harmonics debts left open by v1.4 (the `H{h}-{k}`
naming contract, `find_aspect_timing` orb derivation, and the `--harmonics h7` CLI surface),
and ship `ketu==1.5.0`.

**Axis order (BINDING):** Phases 33 (declination) and 34 (harmonics debt) were fully
independent (either order). Phase 35 (release) followed both — LAST and user-checkpoint-gated.

**Cross-cutting constraints (held):**

- Additive minor — NO breaking changes. `is_ascending` (ecliptic latitude β) stays
  byte-for-byte UNCHANGED; the frozen 14-row `core.aspects` table and its V1/V13 sha256
  preset fingerprints stay byte-identical throughout.
- Pure-NumPy runtime NON-NEGOTIABLE — declination reuses the verified `coordinates.py`
  chain (Meeus 13.4 equivalent); δ-velocity mirrors the `lat_velocity` finite-difference
  idiom; harmonics are plain NumPy angle arithmetic. No scipy, no new runtime deps, no
  `pyswisseph` at runtime.
- All new calculations vectorizable over date arrays; no Python loops in hot paths.
- The only dtype change (`body_decl` in `CHART_DTYPE`) is additive and guarded by a ratchet
  test (analogue of the 13→14 body-count ratchet); positional/`.view()` impact (Kala)
  documented in UPGRADING.
- 100% coverage (`fail_under=100`, zero pragma) + numpydoc + mypy `--strict` BLOCKING.
- Release: pushed `origin/main` AND the tag (RTD follows main, PyPI follows tag);
  user go/no-go gate before any irreversible publish (relecture-validation).

## Phases

### Phase 33: Lunar Declination δ

**Goal**: A user can compute any body's equatorial declination δ (scalar and vectorized over date arrays), its rate of change, the Moon's biodynamic montant/descendant trajectory, and out-of-bounds state — and every computed chart (and the relational/predictive charts that inherit from it) carries declination in a new `body_decl` field, with the feature documented en + fr. All additive: `is_ascending` (ecliptic latitude β) stays byte-for-byte UNCHANGED.
**Depends on**: Nothing (first v1.5 phase; fully additive; reuses the existing `coordinates.py` chain). Independent of Phase 34.
**Requirements**: DECL-01, DECL-02, DECL-03, DECL-04, DECL-05, DECL-06, DECL-07, DECL-08, DECL-09
**Plans**: 4 plans — ✅ COMPLETE 2026-06-03

Plans:

- [x] 33-01: Core declination functions (declination / declination_velocity / is_ascending_declination / is_out_of_bounds) + unit & Meeus-equivalence tests (DECL-01..06) [Wave 1]
- [x] 33-02: body_decl in CHART_DTYPE + compute_chart wiring + dtype ratchet (DECL-07 chart half, DECL-08) [Wave 2]
- [x] 33-03: Downstream propagation — composite explicit populate (zero-fill trap) + returns inheritance test + synastry no-op (DECL-07 downstream) [Wave 3]
- [x] 33-04: Docs en + fr — 4 functions, montant/descendant + β-vs-δ + OOB framing, changelog, FR .po translated & recompiled (DECL-09) [Wave 4]

**Details:**
Declination is computed via the direct Meeus eq. 13.4 formula (`sin δ = sin β·cos ε + cos β·sin ε·sin λ`), guarded by a regression test asserting equality with the existing rectangular `coordinates.py` chain (verified Δ = 0 to machine precision). δ-velocity mirrors the existing `lat_velocity` forward-finite-difference idiom (step 0.01 d) — no wraparound correction since δ ∈ [−90, +90] is bounded and monotone through zero. The montant/descendant helper `is_ascending_declination` is the equatorial analogue of `is_ascending` and does NOT collide with it (β and δ are distinct quantities; anchor 2025-03-07 confirms they do not flip on the same days). OOB uses the instantaneous obliquity ε(jd) (`true_obliquity`), physically correct and free. `body_decl` is added as `("body_decl", "f8", (14,))` parallel to `body_lats`, a deliberate dtype-version bump with a ratchet test mirroring the prior `test_dtype.py` pattern; composite `body_decl` is derived via the coordinates chain on composite λ,β (NOT a midpoint of parents' δ). Largest new-surface v1.5 phase. See `.planning/research/DECLINATION.md`.

### Phase 34: Harmonics Debt (ASP-F1/F2/F3)

**Goal**: The three dynamic-harmonics debts left open by v1.4 are paid down — the synthetic off-table aspect naming scheme `H{h}-{k}` is a documented, pinned public API contract; `find_aspect_timing` can derive its dynamic orb itself from a coefficient instead of the caller passing it raw; and a user can request an arbitrary harmonic on the CLI via `--harmonics h7` — all while the frozen 14-row `core.aspects` table and its V1/V13 sha256 preset fingerprints stay byte-identical.
**Depends on**: Nothing (independent of Phase 33; relies only on the v1.4 dynamic-harmonics engine already shipped). Internal order F2 → F3 → F1 (the CLI surface depends on the naming contract being stable).
**Requirements**: HARM-01, HARM-02, HARM-03, HARM-04, HARM-05, HARM-06, HARM-07, HARM-08, HARM-09
**Plans**: 4 plans in 3 waves (F2 → F3 → F1) — ✅ COMPLETE 2026-06-03

Plans:

- [x] 34-01: F2 (HARM-01..03) — pin the `H{h}-{k}` naming contract (TestNamingContractF2), promote it to the generator docstring, document the GENERATOR-vs-DETECTION two-channel distinction + traditional-name table (en + fr). No code change.
- [x] 34-02: F3 (HARM-04..05) — add `dyn_coef` to `find_aspect_timing` (explicit-orb-first 3-branch, silent precedence), TestFindAspectTimingF3, docs en + fr.
- [x] 34-03: F1 engine (HARM-06..07) — `HarmonicsSelection` NamedTuple + `^h(\d+)$` branch, `print_aspects` dynamic_specs (Quadrinovile bug fix), `cmd_aspects`/`emit_resolved_config`/parser wiring, all broken assertions updated + TestHarmonicTokenF1 + h7 integration.

**Details:**
Internal implementation order F2 → F3 → F1: the naming contract first because the CLI surface depends on it being stable; then `find_aspect_timing` orb derivation; then the CLI. The `H{h}-{k}` contract is frozen across v1.5+ minor/patch releases (the `(h, k) → name/angle/coef` mapping never changes; adding new `h` support never alters existing rows). DETECTION stays static-first — 120° always Trine (i_asp=9), never H3-1. `find_aspect_timing` gets `dyn_coef: Optional[float] = None` (clean under mypy `--strict`); explicit `orb` wins silently when both given (no ValueError); the orb formula mirrors `calculate_aspects:215-216` exactly (single canonical formula). The v1.1 fixture stays byte-identical; a new `--harmonics h7` fixture was generated and manually audited per the ketu ritual (H7-k names, no Quadrinovile, septile angles, U+00BA degree symbol). `core.aspects` V1/V13 fingerprints byte-identical, `core.py` untouched. See `.planning/research/HARMONICS_DEBT.md`.
