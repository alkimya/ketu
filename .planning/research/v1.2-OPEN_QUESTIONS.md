# v1.2 Open Questions

**Status:** Pre-research. Questions deliberately left open for the `/gsd-new-milestone` flow to resolve via questioning + research. Captured 2026-05-08.

## To resolve during questioning phase

### Q1 — Chart abstraction (architectural, upstream of 3 features)

Synastry, composite chart, and solar return all need a "fully resolved chart" primitive that doesn't exist in v1.1. Three options:

- **A.** `CHART_DTYPE` structured array (NumPy-first, batchable, ML-interop friendly)
- **B.** `Chart` dataclass holding constituent NumPy arrays (Pythonic, less batchable)
- **C.** Keep flat — synastry/composite/solar-return each take 4-6 parameters

This decision is upstream of three Tier 1 features. Get it wrong, all three pay. Recommend a dedicated discussion phase early in v1.2 — don't let this leak across plan implementations implicitly.

### Q2 — Composite chart variant

Two variants exist in the literature:

- **Midpoint composite** — `composite_lon(i) = midpoint(natal_A_lon(i), natal_B_lon(i))` — the standard
- **Davison composite** — chart for the midpoint *time* and midpoint *location* of the two natals

Recommend midpoint composite for v1.2 (universally implemented, simpler math). Davison can be a v1.3 add if user demand surfaces.

### Q3 — Arabic Parts: how many to ship?

- **Minimum viable:** Part of Fortune only (covers ~80% of real usage)
- **Hellenistic standard:** seven Hermetic Lots (Fortune, Spirit, Eros, Necessity, Courage, Victory, Nemesis)
- **Maximalist:** the above + relational Parts (Marriage, Children, Death...)

The framework cost is fixed — it's a registry. The marginal cost of each additional Part is ~5 lines of code + a test. Recommend: ship the framework + 7 Hermetic Lots + Part of Marriage (relational synergy with synastry).

### Q4 — Solar return relocation

Standard solar return: chart cast for natal lat/lon at the moment Sun returns to natal longitude.

Relocated solar return: same time, but recomputed houses for a different lat/lon (e.g., where the user lives now vs where they were born). Very common in modern predictive practice.

Recommend: support both. The relocation is just `calculate_houses(jd_return, new_lat, new_lon, system)` after the time is resolved — almost free if the Chart abstraction (Q1) is right.

### Q5 — Tier 3 ordering

Both deadline-driven items must close before September 2026 (Node 20 deprecation):
- `interrogate` + `numpydoc validate` CI wiring
- Workflow Node.js 20 → 24

These are independent. Recommend: wire docs gates early (Phase 1-2 territory; touches all subsequent code) and refresh workflows late (Phase N-1 or N; isolated change). But the user may prefer the inverse if they want to clear the deadline pressure first.

### Q6 — Backward compat framing

v1.1 had three BREAKING items (Lilith ~180° shift, CLI default flip, `calculate_house_cusps` removal). v1.2 should ship as a clean **non-breaking minor**. This means:

- All new APIs are additive (`calculate_synastry`, `compute_chart`, etc.)
- No default changes on existing APIs
- No removed exports

Confirm with user: is this the framing? Or are there v1.1 decisions they want to revisit and break?

## To resolve during research phase (deeper questions for the four parallel agents)

### Architecture researcher

- **AR-Q1:** Does the existing `core` / `aspects` / `houses` / `ephemeris` subpackage layout suggest a new `charts/` subpackage for synastry/composite/solar-return, or should each go in its own subpackage (`synastry/`, `predictive/`...)? The convention from v1.1 was domain-per-subpackage.
- **AR-Q2:** Where does the `Chart` abstraction live? `core.py` (alongside structured-array dtypes)? A new `chart.py`? Inside `charts/` if we go subpackage?
- **AR-Q3:** Whole Sign and Equal are degenerate "houses" — they're trivial functions of the ASC. Does the existing `SYSTEMS` registry handle that gracefully, or does it need a `trivial_systems` tier?

### Features researcher

- **FR-Q1:** What's the dominant Synastry output shape in pro tools (Solar Fire, Astro.com, Kepler)? Dense N×M matrix? Filtered list of orbed aspects? Both?
- **FR-Q2:** Standard orb conventions for synastry vs natal — synastry typically uses *tighter* orbs (3-5°) than natal (8-10° for majors). Should `calculate_synastry` accept its own `orbs=` param defaulting to a tighter set, or reuse natal orbs?
- **FR-Q3:** Solar return orb convention — typically arc-second precision required for the time root-finding. What's the convergence tolerance? Most tools target <1 second of arc.
- **FR-Q4:** Is "Lunar return" (Moon back to natal Moon longitude, ~monthly) in scope? Same algorithm as solar return with a 28-day search window. Cheap to add if solar return is done.

### Pitfalls researcher

- **PR-Q1:** Newton-Raphson on Sun longitude wraps at 360°→0° once per year. How do other implementations handle the search window? Pre-unwrap? Use atan2-style residuals?
- **PR-Q2:** Composite chart midpoint of 359° + 1° should be 0°, not 180°. Confirm pure-NumPy modular midpoint formula and add a test fixture for this exact case.
- **PR-Q3:** Sect determination edge case: Sun exactly on the ASC (sunrise) or DESC (sunset). Day or night? Most tools say "day" inclusive of sunrise. Confirm convention and pick a sentinel value.
- **PR-Q4:** Synastry across time zones — both charts must use UTC, but users will routinely supply local birth times. Reaffirm: Ketu's contract is "caller converts to UTC". Document this loudly in synastry API docstrings.

### Stack researcher

- **SR-Q1:** Confirm `scipy.optimize.brentq` is NOT being introduced for solar-return root-finding. Pure-NumPy bisection or vectorized Newton step. (Pure-NumPy contract is non-negotiable — see CLAUDE.md.)
- **SR-Q2:** Does `pysweph` cover synastry/composite/solar-return as oracle test sources? It does individual chart calculations but the relational/return derivations are caller-side. Test fixtures may need to be hand-validated against Astro.com or Solar Fire.
- **SR-Q3:** Are `interrogate` and `numpydoc` already in `[project.optional-dependencies]`? Check before assuming a `pip install` is needed.
